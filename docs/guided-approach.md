# Guided approach: relative UWB + live LiDAR

Use **Locate → Guided approach on the can phone**. This is a reactive approach controller: it turns toward the player and advances when the observed forward lane passes the checks. If blocked, it stops; it does not plan around objects. Calculations run on iPhone. The Pi executes the same simple authenticated commands it already supports.

## Phone-only preview

1. Install the updated app on both phones and connect with their can/player roles. Enable camera-assisted bearing. Leave the Pi URL empty for a standalone preview; disconnect motor power for a handheld test.
2. Mount/hold the can phone at the assumed 44 cm lens height, rear camera forward and slightly down. Confirm the existing Locate angle changes correctly when turning toward/away from a stationary player.
3. Stay in Locate; close Lab. Tap **Preview guidance** and choose a 1/2/3 m stopping distance. No motor command is generated by preview decisions.
4. The card should say **Turn left/right** when misaligned, **Forward** when facing the player with observed floor ahead, and **Arrived** within the chosen distance plus 15 cm. These are proposed commands until you explicitly start driving.
5. Place a box inside the 46 cm forward corridor, closer than 75 cm: decision should be **Blocked**. Remove it: preview should recover to a movement suggestion. Obscure the camera or stop the player session: decision should be **Stop**. Turning suggestions also require the forward checks to pass.

## Movement test

1. Set the same Pi URL/token 12345 on both phones, connect, and run the existing `python3 pi/server.py`. The bridge must be enabled and stopped, with no active command. A hold left over from Lab must be released first.
2. Verify wheel directions with existing manual controls. The phone's forward/right must match the chassis forward/right. Use a controlled clear arena with a spotter and the motor-power kill switch.
3. On the can phone in Locate, start preview. With a valid movement suggestion, tap **Start guided approach**. This explicitly enables motor commands; preview does not start them automatically.
4. Initial output is fixed at 50% forward / 45% pivot in the Pi command scale, still subject to its 130/255 PWM duty cap. These are command percentages, not measured speed or voltage. Motor deadband, traction, load and stopping distance must be checked on hardware.
5. **Stop**, leaving Locate, opening Lab, disconnecting/backgrounding, arrival, blocked/unknown sensor state, or control failure ends the run. Recovery only changes the preview suggestion; press Start again to move. Player manual/legacy Summon starts are disabled while guided mode is announced active, but Player Stop remains available.

## Current checks and limits

- Can-side UWB distance and bearing must both be finite, connected and less than 250 ms old. Distance alone cannot steer. Uses the existing Locate bearing directly; no map-coordinate conversion.
- Movement acknowledgements must keep arriving within 250 ms; malformed/non-confirming replies stop the run. A slow connection can therefore stop guidance even before the Pi watchdog fires.
- LiDAR must be less than 400 ms old with Normal ARKit tracking and an initialized assumed floor. Processing is 5 Hz. Sensor checks run at 10 Hz; the Pi independently stops after 300 ms without renewed commands. These are freshness limits, not measured total stopping latency.
- Obstacle within 75 cm in the forward lane blocks all movement; at least 65 cm of consecutively observed floor must also be available. That floor-coverage heuristic does not prove the entire lane is clear.
- Turn begins above about 13° error and continues until within about 6°, reducing repeated switching between turning and forward. Positive Locate bearing requests right; validate actual mounting and motor polarity.
- Stopping distance is phone-to-phone slant range, not distance from bucket edge to the player's body. Different phone heights affect it.
- Current LiDAR filtering still omits depths below 15 cm and low-confidence returns. Low obstacles, hidden geometry and sides/rear are not covered. The front-facing camera cannot certify the swept area of a turn: keep the surroundings clear. Ultrasonic sensing is not integrated into this mode yet.
- No encoders, dynamic braking model, route planner, learned person detector or automatic rearming are added here. ARKit continues to support UWB camera assistance and depth floor geometry.

## Verification

Pure Swift checks cover relative steering signs, turn hysteresis, fixed speed commands, arrival, missing/invalid/stale UWB/depth, unknown floor and close obstacles. Simulator checks verify guided movement cannot start without hardware and existing offline screens remain responsive. Actual driving, sensor alignment, motor deadband and stopping behavior require the physical robot.
